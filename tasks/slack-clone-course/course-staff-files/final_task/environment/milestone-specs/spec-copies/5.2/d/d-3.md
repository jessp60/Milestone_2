# D.3: a killed Redis does not stop fan-out

Check: `bash /spec/d/checks/check_d_3.sh`. The rule numbers below match its output.
This check kills the Redis server with `SIGKILL`.

All routes are under `/api/...`, return JSON, and take `Authorization: Bearer <token>`. The three HTTP nodes listen on `127.0.0.1:8000`, `:8001` and `:8002`. Status codes unless a rule says otherwise: `200` on read/update success, `201` on create, `400` on validation, `401` on missing or invalid auth, `403` on auth-but-forbidden, `404` on unknown id, `409` on conflict, `413` on upload over limit, `423` on writes to an archived channel. Every request must answer within 5 seconds.

WebSocket: `ws://127.0.0.1:800x/api/ws?token=<bearer>`, one JSON frame per message. Client frames: `{"type":"subscribe","channel_id":N}` is answered with `subscribed` carrying `channel_id` and an integer `head_event_id`; `{"type":"resume","channel_id":N,"since_event_id":E}` replays every event after `E` in order and then sends `resumed` with `head_event_id` equal to the last event id. A new message is broadcast as `message.created` with `channel_id` and an integer `event_id`. Event ids in a channel are dense: the first is `head_event_id + 1`, then exactly +1 each, and every node shows the same ids.

Important: the checks stop a process with `SIGKILL` by the PID that owns its port. Run each node as its own process that listens on exactly one of the ports `8000`, `8001`, `8002` (not one process that holds all three), so that killing one leaves the other two running. Never stop processes by name (`pkill -f`, `killall`, `pgrep -f`).

Do not start this spec until `check_d_2.sh` passes.

## Uses

Everything from D.1 and D.2.

## Adds

| Function | What it does |
|---|---|
| Redis fan-out | a local `redis-server` on `127.0.0.1:6379` carries events between the nodes |
| outage fallback | when Redis dies, nodes still deliver events to each other, with no gap in `event_id` |
| Redis respawn | `/app/start.sh` starts Redis again after it dies |

## Rules

The cluster must run a local Redis pub/sub daemon on `127.0.0.1:6379`. If `redis-server` is not installed, look for it with `which redis-server` and install it with the package manager that works in your container.

3.1 **Redis is up.** A Redis server answers `PING` with `+PONG` on `127.0.0.1:6379`.

3.2 **Fan-out works.** Before the outage, a post on node 0 reaches a `message.created` subscriber on node 1.

3.3 **Writes survive.** After the process that owns port 6379 is killed with `SIGKILL`, writes return `201` on node 0, node 1 and node 2 within 5 seconds.

3.4 **Events still cross nodes.** During the outage a subscriber on node 1 still receives `message.created` for posts made on nodes 0 and 2, within 5 seconds of the kill.

3.5 **No gap.** The `event_id` values for the channel stay consecutive across the outage and are identical on all three nodes.

3.6 **Respawn.** `PING` on `127.0.0.1:6379` answers again within 15 seconds of the kill without anyone starting Redis by hand.

3.7 **Recovery.** After Redis is back, a post on node 2 reaches a subscriber on node 0 and the event ids are still consecutive.

3.8 **Nodes alive.** All three HTTP nodes still answer `GET /api/health`.
