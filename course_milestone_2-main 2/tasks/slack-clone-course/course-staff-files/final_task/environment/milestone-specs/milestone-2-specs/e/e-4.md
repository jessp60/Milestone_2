# E.4: the web UI page

Check: `bash /spec/e/checks/check_e_4.sh`. The rule numbers below match its output.

All routes are under `/api/...`, return JSON, and take `Authorization: Bearer <token>`. The three HTTP nodes listen on `127.0.0.1:8000`, `:8001` and `:8002`. Status codes unless a rule says otherwise: `200` on read/update success, `201` on create, `400` on validation, `401` on missing or invalid auth, `403` on auth-but-forbidden, `404` on unknown id, `409` on conflict, `413` on upload over limit, `423` on writes to an archived channel. Every request must answer within 5 seconds.

## Uses

The three HTTP nodes and the REST API the page calls.

## Adds

| Function | What it does |
|---|---|
| single-page app | `GET /` on any node returns the app, a three-pane Slack-like page that a browser agent can drive |

## Rules

These rules cover what a script can read from the served page. The grader also drives the page in a browser at 1280x900 (sign-up with a visible error on invalid input, logout and login, channels, posting, editing and deleting with a hover toolbar and an "edited" indicator, threads in a right-hand panel, an emoji-picker grid for reactions, an empty-channel message, a three-pane layout). Build for that too, even though no script here checks it.

4.1 **Served.** `GET /` returns `200` with an HTML page on all three nodes.

4.2 **Test ids.** The initial HTML contains an element with each of these `data-testid` values: `auth-form`, `auth-submit`, `auth-toggle`, `workspace-create-form`, `empty-state-create-workspace`, `join-workspace-form`, `join-workspace-submit`, `channel-list`, `dms-list`, `new-channel-btn`, `current-user`, `logout-btn`, `workspace-header`, `workspace-settings-btn`, `workspace-settings-close`, `workspace-name-input`, `workspace-join-mode`, `workspace-general-submit`, `channel-title`, `channel-topic`, `channel-settings-btn`, `channel-settings-title`, `channel-settings-close`, `channel-members-list`, `channel-add-member-form`, `channel-add-member-input`, `channel-add-member-submit`, `channel-topic-input`, `channel-topic-submit`, `archive-channel-btn`, `unarchive-channel-btn`, `create-channel-form`, `create-channel-private`, `create-channel-submit`, `create-channel-cancel`, `message-list`, `message-input`, `send-btn`, `thread-panel`, `thread-input`, `thread-send`, `close-thread`, `settings-tab-members`, `settings-tab-invitations`, `settings-tab-general`, `settings-pane-members`, `settings-pane-invitations`, `settings-pane-general`, `create-invitation-btn`, `create-invitation-form`, `create-invitation-submit`, `invitations-list`. The data-dependent ones (`channel-entry`, `message`, `message-body`, `open-thread-btn`, `reaction-button`, `reaction-chip`, `emoji-picker`, `emoji-option`, `member-row`, `role-badge`, `role-select`, `invitation-code`, `channel-member-row`, `join-workspace-error`) are created when the page renders them.

4.3 **DOM ids.** The initial HTML has elements with the ids `auth-modal`, `create-channel-modal`, `channel-settings-modal`, `workspace-settings-modal` and `create-invitation-form`.

4.4 **Button roles.** Each of these buttons carries a `data-button-role` attribute in the initial HTML: role `primary` for `auth-submit`, `send-btn`, `thread-send`, `create-channel-submit`, `join-workspace-submit`, `workspace-general-submit`, `create-invitation-submit`, `channel-topic-submit`, `channel-add-member-submit`; role `danger` for `archive-channel-btn`, `logout-btn`; role `secondary` for `new-channel-btn`, `create-invitation-btn`, `unarchive-channel-btn`, `create-channel-cancel`, `close-thread`, `channel-settings-close`, `workspace-settings-close`, `channel-settings-btn`, `workspace-settings-btn`.

4.5 **Colours.** In their resting state the three roles use exactly these colours with white text: `primary` `#007a5a`, `danger` `#e01e5a`, `secondary` `#1264a3`, as plain colours (no gradients, images or transparency). The page's styles contain all three values.

4.6 **Token storage.** After login the page keeps the bearer token under the localStorage key `huddle.token`. The page code contains that key.

4.7 **Same page everywhere.** Nodes 1 and 2 serve the same pinned elements as node 0.
