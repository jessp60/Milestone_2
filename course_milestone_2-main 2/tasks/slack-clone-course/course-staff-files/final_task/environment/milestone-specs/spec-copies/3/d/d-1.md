# D.1: a killed HTTP node does not stop the cluster

Check: `bash /spec/d/checks/check_d_1.sh`. The rule numbers below match its output.
This check kills the node on port 8001 with `SIGKILL`, so run it when you are ready for that.

All routes are under `/api/...`, return JSON, and take `Authorization: Bearer <token>`. The three HTTP nodes listen on `127.0.0.1:8000`, `:8001` and `:8002`. Status codes unless a rule says otherwise: `200` on read/update success, `201` on create, `400` on validation, `401` on missing or invalid auth, `403` on auth-but-forbidden, `404` on unknown id, `409` on conflict, `413` on upload over limit, `423` on writes to an archived channel. Every request must answer within 5 seconds.

WebSocket: `ws://127.0.0.1:800x/api/ws?token=<bearer>`, one JSON frame per message. Client frames: `{"type":"subscribe","channel_id":N}` is answered with `subscribed` carrying `channel_id` and an integer `head_event_id`; `{"type":"resume","channel_id":N,"since_event_id":E}` replays every event after `E` in order and then sends `resumed` with `head_event_id` equal to the last event id. A new message is broadcast as `message.created` with `channel_id` and an integer `event_id`. Event ids in a channel are dense: the first is `head_event_id + 1`, then exactly +1 each, and every node shows the same ids.

Important: the checks stop a process with `SIGKILL` by the PID that owns its port. Run each node as its own process that listens on exactly one of the ports `8000`, `8001`, `8002` (not one process that holds all three), so that killing one leaves the other two running. Never stop processes by name (`pkill -f`, `killall`, `pgrep -f`).

## Uses

Users, workspaces, a `#general` channel, `POST` and `GET /api/channels/{id}/messages`, the WebSocket above, and state that all three nodes share.

## Adds

| Function | What it does |
|---|---|
| node isolation | each node is its own process, so one dying does not take down the others |
| survivor service | the two living nodes keep serving reads, writes, WebSocket frames and replay |

## Rules

1.1 **Before the kill.** A message posted on node 0 reaches a `message.created` subscriber on node 2 (the setup works).

1.2 **Survivors answer.** After the process that owns port 8001 is killed with `SIGKILL`, nodes 0 and 2 still answer `GET /api/health` with `200` within 3 seconds.

1.3 **Reads.** `GET /api/channels/{id}/messages` works on both surviving nodes and shows the message posted before the kill.

1.4 **Writes.** `POST /api/channels/{id}/messages` returns `201` on node 0 and on node 2, and each message is visible in the listing of the other node.

1.5 **WebSocket delivery.** A subscriber on node 0 receives `message.created` for a post made on node 2, and a subscriber on node 2 receives it for a post made on node 0.

1.6 **Dense event ids.** The `event_id` values the two survivors show for the channel are consecutive across the kill and identical on both nodes.

1.7 **Dropped connection.** A WebSocket that was connected to the killed node closes (the client sees the connection end within 3 seconds).

1.8 **Replay.** A client that reconnects to node 2 and sends `resume` with the last event id it saw before the kill receives every event it missed, in order, followed by `resumed`.
