# E.2: the IRC gateway

Check: `bash /spec/e/checks/check_e_2.sh`. The rule numbers below match its output.

All routes are under `/api/...`, return JSON, and take `Authorization: Bearer <token>`. The three HTTP nodes listen on `127.0.0.1:8000`, `:8001` and `:8002`. Status codes unless a rule says otherwise: `200` on read/update success, `201` on create, `400` on validation, `401` on missing or invalid auth, `403` on auth-but-forbidden, `404` on unknown id, `409` on conflict, `413` on upload over limit, `423` on writes to an archived channel. Every request must answer within 5 seconds.

## Uses

Users and their bearer tokens, workspaces, channels, `POST` and `GET /api/channels/{id}/messages`, and the WebSocket `message.created` event with its dense per-channel `event_id`.

## Adds

| Function | What it does |
|---|---|
| IRC gateway | a TCP server on `0.0.0.0:6667` that speaks IRC and shares messages with the web side |

## Rules

Lines end in `\r\n`. A client logs in with `PASS <bearer token>`, then `NICK <nick>` and `USER <user> 0 * :<real name>`. A web channel is the IRC channel `#{workspace-slug}/{channel-name}` (for example `#acme/general`). The separator is a literal `/`.

2.1 **Bad password.** `PASS` with a token that is not valid is answered with numeric `464`.

2.2 **Registration.** A valid login is answered with numerics `001` to `005` in order, followed by `422` (no MOTD).

2.3 **Unknown channel.** `JOIN` of a channel that does not exist is answered with `403`.

2.4 **Nick in use.** `NICK` with a nick another connection uses is answered with `433` and the connection stays open; a different nick then registers.

2.5 **Unknown command.** A command the gateway does not know is answered with `421`.

2.6 **Join.** `JOIN #{slug}/general` sends the joiner's own `JOIN` line (`:nick!user@host JOIN #{slug}/general`), then `353` (names, listing the nick), then `366`.

2.7 **Hyphen form.** `JOIN #{slug}-general` is an unknown channel (`403`).

2.8 **Ping.** `PING :token` is answered with `PONG` carrying the same token.

2.9 **IRC to web.** `PRIVMSG #{slug}/general :text` from an IRC client creates a message that `GET /api/channels/{id}/messages` shows, on every node.

2.10 **Web to IRC.** A message posted through the web API reaches IRC clients that joined the channel as `:<nick>!<user>@<host> PRIVMSG #{slug}/general :<body>`.

2.11 **One event stream.** Messages written from IRC and from the web in turn get consecutive `event_id` values in the same per-channel stream, as seen by a WebSocket subscriber.

2.12 **Quit.** `QUIT` closes the connection and sends no error reply (no `ERROR` line, no numeric of 400 or above).

2.13 **Other commands.** `NAMES`, `WHO`, `LIST`, `TOPIC` and `MODE` are accepted (never answered with `421`) and the connection stays up.
